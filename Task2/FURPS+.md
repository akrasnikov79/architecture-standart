# Требования к системе открытия депозитов (FURPS+)

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| **F** | **Функциональные (Functionality)** | |
| | Витрина: отображение списка депозитов и ставок на сайте (для новых) и в ИБ (в т.ч. персонализированные предложения). | MVP |
| | Подача заявки на сайте (ввод ФИО, номера телефона). | Передача в систему КЦ |
| | Подача заявки в интернет-банке (выбор счета и суммы). | |
| | Подтверждение подачи заявки в ИБ с помощью СМС-кода. | Функционал СМС уже есть в ядре, реализуется силами банка. |
| | Ведение ставок по депозитам в АБС и процесс согласования ставки бэк-офисом. | Архитектурно-значимое: отказ от Excel. |
| | Отправка СМС-уведомлений клиенту при подтверждении ставки и открытии депозита. | Решение на стороне АБС / шлюза. |
| | Обработка онлайн-заявок менеджером бэк-офиса с подтверждением в АБС (MVP). | Временное решение до полной автоматизации. |
| **U** | **Удобство использования (Usability)** | |
| | Интерфейс должен соответствовать принятой корпоративной дизайн-системе. | Привычные брендированные элементы, цвета. |
| | Интуитивно понятный и максимально удобный пользовательский опыт (UX) при открытии депозита. | |
| **R** | **Надёжность (Reliability)** | |
| | Доступность сервисов 24/7 (SLA 99,9%). | Архитектурно-значимое: требует балансировки и отказоустойчивости. |
| | Работоспособность ИБ при сбое основного ЦОД (переключение на резервный ЦОД). | Развертывание active-passive или active-active контура в резервном ЦОД. |
| | Система должна поддерживать равномерное горизонтальное масштабирование и балансировку запросов. | Относится к ИБ, API-шлюзам и микросервисам. |
| **P** | **Производительность (Performance)** | |
| | Быстрый отклик системы: все операции (в т.ч. загрузка справочников) должны выполняться за миллисекунды. | Архитектурно-значимое: требуется кэширование, так как сейчас загрузка >1 сек. |
| | Защита базы данных АБС от перегрузок при онлайн-подаче заявок. | Исключение прямой синхронной записи интернет-банка в БД АБС. |
| **S** | **Поддерживаемость (Supportability)** | |
| | Возможность расширения: разработка исчерпывающей документации на новые компоненты и API. | |
| | Совместимость с текущими технологиями: использование MS SQL, Oracle, C# .NET, Java Spring Boot, React. | Снижение Time-to-Market за счет имеющейся экспертизы. |
| | Потенциальный переход ИБ на микросервисную архитектуру (в рамках задачи депозитов). | Архитектурно-значимое: выделение сервиса депозитов из монолита. |
| **+R** | **+ Ограничения (Restrictions / Констрейнты)** | |
| | Безопасность: Обязательное шифрование трафика (SSL/TLS) с сайта и в ИБ при передаче чувствительных данных. | Требование ИБ/Security. |
| | Безопасность/Compliance: обязательная очная идентификация новых клиентов (с сайта) в отделении. | Законодательное ограничение (ПОД/ФТ). |
| | Технологическое: использование Apache Kafka для асинхронного взаимодействия «на перспективу». | Возможна разработка адаптера/фасада для монолита ИБ. |
| | Технологическое: АБС масштабируется только вертикально. | Жесткое ограничение со стороны вендора/архитектуры БД Oracle. |
