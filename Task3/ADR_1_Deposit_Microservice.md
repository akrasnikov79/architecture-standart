## Выделение Deposit Service из монолита Интернет-банка (L2 Container)

### Context and Problem Statement
Текущий Интернет-банк представляет собой монолитную систему на базе устаревшего фреймворка ASP.NET 4.5. Развитие нового функционала — онлайн-открытия депозитов — сопряжено с высоким Time-to-Market, риском поломки существующих модулей (платежей) и ограничениями горизонтального масштабирования. Требуется определить архитектурный подход к реализации витрины депозитов и процессингу заявок.

### Considered Options
1. Реализация нового функционала внутри существующего монолита ИБ (ASP.NET 4.5).
2. Выделение отдельного развертываемого микросервиса `Deposit Service` на современном стеке (ASP.NET Core).

### Decision Outcome
Выбран вариант 2 (Выделение независимого микросервиса `Deposit Service`). 
Это обеспечит независимый цикл релиза для новой функциональности, позволит использовать современные фреймворки (ASP.NET Core) и даст возможность изолированно масштабировать депозитный сервис в моменты маркетинговых кампаний.

### Consequences
- Быстрый Time-to-Market для MVP депозитов.
- Возможность независимого горизонтального автомасштабирования.
- Изменение ландшафта: потребуется настройка API Gateway (BFF) для склейки фронтенда (SPA) с новым бекендом и старым монолитом.
- Необходимость управления распределенными сессиями/SSO (Single Sign-On).

### Confirmation
Решение зафиксировано на диаграмме контейнеров `C4_Containers.md` в виде изолированного контейнера `Deposit Microservice` и маршрутизирующего `API Gateway`.

### Pros and Cons of the Options

#### Option 1: Разработка внутри монолита
Good, because не требует доработки инфраструктуры (API Gateway, SSO).
Bad, because релиз привязан к подрядчику монолита.
Bad, because невозможно изолированно масштабировать депозитный модуль при высоких нагрузках.

#### Option 2: Выделение микросервиса (Выбран)
Good, because независимый CI/CD и релизы.
Good, because снимает vendor-lock на подрядчика монолита (можно развивать in-house).
Good, because решает задачу масштабирования.
Bad, because повышает сложность DevOps и интеграции UI/API слоя.
