### **Название задачи:** Архитектура MVP для открытия депозитов онлайн
### **Автор:** Архитектор (Antigravity)
### **Дата:** 12.03.2026

### **Функциональные требования (Use Cases)**
|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Новый клиент, Сайт, Система КЦ | Заявка на сайте | Клиент просматривает ставки на сайте и оставляет заявку (ФИО, телефон). Данные уходят в CRM кол-центра. |
| 2 | Менеджер КЦ, Клиент, Система КЦ | Обработка лида | Менеджер КЦ звонит клиенту, консультирует по ставкам, предлагает особые условия (через CRM). |
| 3 | Клиент, Отделение, АБС | Очная идентификация | Клиент приходит в отделение с паспортом для идентификации и подписания договора обслуживания. |
| 4 | Действующий клиент, ИБ | Заявка в ИБ | Клиент видит персонализированные ставки в ИБ, выбирает счет для списания и сумму, подтверждает операцию СМС-кодом. |
| 5 | Менеджер бэк-офиса, АБС | Обработка онлайн-заявки | Менеджер БО видит заявку из ИБ в АБС, согласовывает ставку и подтверждает открытие депозита вручную (для MVP). |
| 6 | СМС-шлюз, АБС | Уведомление клиента | АБС инициирует отправку СМС-сообщения («Ставка подтверждена, депозит открыт»). |

### **Нефункциональные требования**
|**№**|**Требование**|
| :-: | :- |
| 1 | **Доступность (Reliability):** 24/7 (SLA 99.9%). ИБ должен быть развернут в двух ЦОД (основной и резервный) с балансировкой нагрузки для отказоустойчивости. |
| 2 | **Производительность (Performance):** Время отклика ИБ — миллисекунды. Запрещена прямая синхронная запись из ИБ в БД АБС во избежание деградации АБС. Применение кэширования для справочников. |
| 3 | **Масштабируемость:** ИБ должен горизонтально масштабироваться (переход к микросервисной архитектуре). АБС масштабируется только вертикально. |
| 4 | **Безопасность (Security):** Обязательное шифрование (HTTPS/TLS) для Сайта и ИБ. |
| 5 | **Технологические ограничения:** Использование текущего стека (ASP.NET, C#, MS SQL, Oracle, Java) для переиспользования внутренней экспертизы. Kafka пока не используется для прямой интеграции с монолитом ИБ (возможно использование промежуточного REST/gRPC API). |

### **Решение**
В рамках MVP мы реализуем гибридный процесс:
1. Выделяем микросервис «Депозиты» в контуре Интернет-банка (на стеке ASP.NET / MS SQL), который будет обслуживать витрину ставок и принимать заявки от клиентов онлайн.
2. Интеграция с АБС для MVP реализуется через асинхронный обмен (например, через промежуточную таблицу-буфер в БД АБС, куда микросервис Депозитов пишет по защищенному API, либо через REST API АБС, если оно есть).
3. Сохраняем ручную обработку: заявка падает в очередь (в АБС), менеджер бэк-офиса обрабатывает её вручную, утверждает ставку, и депозит создается в АБС. Уведомление уходит через интеграцию АБС -> СМС-шлюз.

Диаграммы контекста и контейнеров в модели C4 предоставлены в смежных файлах `C4_Context.md` и `C4_Containers.md`.

### **Альтернативы**
1. **Прямая синхронная интеграция ИБ с БД АБС.** Отклонено, так как нарушает требование по производительности АБС и рискует "положить" основную систему банка при наплыве заявок.
2. **Полностью автоматическое открытие в АБС (Целевой процесс уже в MVP).** Отклонено из-за высокой сложности доработок АБС. Для MVP выбран компромисс — ручная валидация бэк-офисом.

**Недостатки, ограничения, риски**
- **Риск:** Микросервис депозитов сложно интегрировать с текущим монолитом ИБ (требуется настройка SSO/API Gateway).
- **Ограничение:** Клиенту всё равно нужно ждать подтверждения от бэк-офиса (не мгновенное открытие). Это ухудшает UX, но допустимо для MVP.
- **Риск загрузки БО:** При успешном маркетинге бэк-офис не будет успевать обрабатывать заявки руками, возникнет узкое место (Bottleneck).
