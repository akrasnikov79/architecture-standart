Walkthrough: Рефакторинг Архитектуры по стандартам системного проектирования
Была произведена полная переработка артефактов в репозитории architecture-standart на основе строгого C4, Contract-First и ADR-шаблонов.

Что было сделано
1. Contract-First дизайн
Мы выделили дата-сущности и контракты до диаграмм:

Создана бизнес-модель домена: 
data-model.md
Сконструирован REST API контракт для сервиса депозитов: 
deposit-openapi.yaml
Зафиксирован асинхронный событийный контракт: 
abs-integration-asyncapi.yaml
2. Модели C4
Модели очищены от технологического "мусора" (отсылок к JSON, REST, HTTPS на высоких уровнях абстракции). В иерархию добавлен компонентный уровень L3:

L1 (Context): 
C4_Context.md
 — только бизнес-взаимодействия систем.
L2 (Containers): 
C4_Containers.md
 — выделение ответственности между микросервисом и легаси монолитом, без деталей баз данных.
L3 (Components): 
C4_Components.md
 — новая диаграмма состава Deposit Service (Web Controller, Application Service, Adapters).
3. Архитектурные Решения (ADR)
Старые скомканные документы заменены на 3 атомарных ADR по стандарту отрасли:

Выделение Deposit Service: 
ADR_1_Deposit_Microservice.md
Выбор асинхронной интеграции с АБС: 
ADR_2_ABS_Async_Integration.md
Интеграция с КЦ-партнером (Шифрованный Email): 
ADR_3_Partner_File_Exchange.md
4. Модели поведения
Мы развели сквозные бизнес-процессы и техническое взаимодействие по разным нотациям (согласно антипаттернам навыка architecture):

Бизнес-процесс (BPMN / Collaboration Flowchart): 
Integration_Scheme.md
 — сквозной процесс с "ручниками" и коммуникацией систем.
Технический процесс (UML Sequence): 
Sequence_Deposit_Creation.md
 — строгий timing взаимодействия через брокер (Kafka).
Валидация
Задача системной архитектуры выполнена: артефакты четко описывают "что нужно создать" (OpenAPI), "где оно живет" (C4) и "почему так решено" (ADR).
